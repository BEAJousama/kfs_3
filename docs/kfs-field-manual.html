Everything the three kernels touch, explained

This manual walks the full path from an empty compiler to a paging kernel with its own allocator: the boot handshake, protected mode, the GDT and IDT, the PIC and the keyboard, then virtual memory and two heaps. Every concept is tied back to the code in kfs_2 and kfs_3.

00

Three kernels, one machine

What each project adds, and the mental model that ties them together.

The series builds one 32-bit x86 kernel in three passes. Each pass is a self-contained subject, but the later ones start from the earlier code.

ProjectThemeWhat you end up with
KFS_1Boot & screenA Multiboot kernel GRUB can load, printing to the VGA text buffer. A tiny printf, scrolling, keyboard echo.
KFS_2The CPU's tablesA GDT (segmentation), an IDT with 32 exception handlers, the PIC remapped, IRQ handlers, a real keyboard driver, a debug shell, kernel panics.
KFS_3MemoryPaging turned on, a physical frame allocator, and two heaps: kmalloc (physically contiguous) and vmalloc (virtually contiguous).

The one model to hold in your head

A CPU running your kernel is a state machine driven by three things: the instruction pointer (what runs next), a set of tables in RAM that the CPU consults on every instruction (the GDT for segment meaning, the page tables for address meaning, the IDT when something interrupts), and control registers that say which mode those lookups happen in. Almost everything in KFS_2 and KFS_3 is "fill in a table, then point a register at it, then execute a magic instruction that makes the CPU start using it."

  • lgdt + a far jump → the CPU now interprets segment selectors through your GDT.
  • lidt → interrupts and faults now vector through your IDT.
  • mov cr3 + set CR0.PG → every address is now translated through your page tables.
Note

"Bare metal" here does not mean the CPU starts blank. GRUB has already switched it to 32-bit protected mode with a throwaway GDT and paging off before your _start runs. Your job in KFS_2/3 is to replace those temporary structures with ones you control.

01

The cross-compiler & freestanding C

Why you cannot use the gcc already on your machine, and what every compiler flag in the Makefile is buying you.

What "cross" means

A compiler is described by three platforms: the machine it runs on (host), the machine it builds for (target), and — for a compiler that builds compilers — the machine that built it (build). Your distro's gcc is a native compiler: host = target = your Linux box. It assumes the things your Linux box provides — a C library, a dynamic loader, an executable format with an OS behind it, a specific default GDT layout, stack protection hooks, position-independent code for ASLR.

Your kernel has none of that. It needs a cross-compiler whose target is a bare ELF x86 machine with no operating system: the triple i686-elf.

Triple partMeaning
i686The CPU: 32-bit x86, Pentium Pro era instruction set. (i386 works too; i686 just lets the compiler assume a few more instructions.)
(no vendor)No "pc", no "linux". Nothing is assumed about the platform.
elfOutput format is plain ELF with no OS ABI. No libc, no syscalls, no dynamic linker.

Building it (the install_gcc_cross.sh / scripts/provision.sh script) is two steps:

  1. binutils configured with --target=i686-elf — this gives you i686-elf-as (assembler), i686-elf-ld (linker), i686-elf-objdump, etc. that emit and understand 32-bit ELF regardless of your host.
  2. gcc configured the same way with --without-headers (there is no libc to find headers for) and --enable-languages=c,c++. You build all-gcc and all-target-libgcc — the compiler itself plus libgcc.

Why libgcc is the one library you do link

The 32-bit x86 CPU has no instruction for 64-bit division, 64-bit modulo, or some shifts. When your C code writes uint64_t a / b, gcc emits a call __udivdi3 — a helper function that lives in libgcc.a. That is why the link line ends with -lgcc. It is compiler runtime support, not an operating-system library, so it is allowed.

Every flag in the Makefile

FlagWhy
-ffreestandingTells gcc this is a freestanding environment: main is not special, and only a handful of headers (stdint.h, stddef.h, stdbool.h, stdarg.h) are guaranteed. The opposite is hosted (a normal program with a C library).
-nostdlibDon't link the standard library or the C runtime startup files (crt0) at link time. Your _start is the entry point.
-nodefaultlibsDon't auto-link any default libraries (belt and braces with -nostdlib).
-fno-builtinDon't assume libc semantics for functions named memcpy, strlen, … so gcc won't, say, replace your loop with a call to a memset that doesn't exist. (You still provide your own in helpers.c; gcc may still emit calls to memcpy/memset for struct copies, which is why you implement those.)
-fno-stack-protectorThe stack-smashing guard calls __stack_chk_fail and reads a canary from a libc-managed global. Neither exists.
-fno-picGenerate position-dependent code. The kernel is linked to run at one known address (2 MiB); it never gets relocated, so the GOT/PLT indirection of PIC is pure overhead — and references _GLOBAL_OFFSET_TABLE_, which nothing defines.
-m32 (host-gcc fallback)If you build with your host gcc instead of the cross one, this forces 32-bit code generation. It works for C, but you're trusting the host's headers and defaults — the cross-compiler is the clean answer.
Gotcha

The subject lets you use the host's ld binary but forbids the host's default linker script. The default script links a normal Linux executable — right entry symbol, wrong load address, expects an interpreter. You must supply your own (Part 03).

Interview

"Why can't you just use gcc on your laptop to build a kernel?" — Because a native gcc bakes in host assumptions: it links against glibc and the C runtime, targets your OS's ELF ABI, emits PIC for ASLR, and inserts stack-protector calls into libc-managed globals. A freestanding kernel has no libc, no loader, and one fixed load address. A cross-compiler configured for i686-elf removes every one of those assumptions; the flags (-ffreestanding -nostdlib -fno-builtin -fno-stack-protector -fno-pic) remove the rest.

02

Power-on to _start

The BIOS, the Multiboot contract, what GRUB hands you, and the twenty lines of assembly that bridge into C.

Real mode, protected mode, and why the jump matters

An x86 CPU powers on in real mode: 16-bit registers, 1 MiB of addressable memory, addresses formed as segment × 16 + offset, no memory protection. This is 1978 compatibility that every x86 chip still boots into.

Protected mode is the 32-bit world: 4 GiB address space, privilege rings, segmentation with real access checks, and (optionally) paging. Switching modes means setting bit 0 of CR0 and loading a GDT — GRUB does this for you. When your kernel later reloads CS with a far jump in gdt_flush, it is finishing that handshake with segments it defined.

Note — the A20 line

On the original 8086, address 0x100000 wrapped to 0. Later CPUs added a gate (the "A20 line") that must be enabled to address memory above 1 MiB without wrap. It is a classic boot-code chore — GRUB handles it before you get control, which is one more reason to boot via a Multiboot loader rather than write a 16-bit bootsector.

The Multiboot contract

Rather than write raw boot sectors, the kernel declares itself Multiboot 1–compliant so any compliant loader (GRUB) will load it. The contract is a header that must appear in the first 8 KiB of the kernel file, 4-byte aligned:

/* boot.s */
.set MAGIC,    0x1BADB002        ; lets the loader find the header
.set FLAGS,    (1<<0) | (1<<1)   ; bit0 = align modules on pages
                                ; bit1 = give me a memory map
.set CHECKSUM, -(MAGIC + FLAGS)  ; MAGIC+FLAGS+CHECKSUM must == 0

.section .multiboot
.align 4
.long MAGIC
.long FLAGS
.long CHECKSUM

The linker script forces .multiboot to the very front of .text so it lands in that first 8 KiB.

What GRUB hands you

When GRUB jumps to your entry point, it guarantees a specific machine state:

  • Protected mode, paging off, interrupts off.
  • A valid but temporary GDT (you must load your own soon and not rely on GRUB's).
  • EAX = 0x2BADB002 — proof you were booted by a Multiboot loader.
  • EBX = physical address of a multiboot_info struct: total memory, a memory map, boot device, command line, module list.
  • ESP is not guaranteed — you must set up your own stack immediately.
In our code

kfs_3/src/boot.s pushes EBX then EAX before call kernel_main, so C receives them as kernel_main(uint32_t magic, multiboot_info_t *mbi). KFS_3 reads mbi->mem_upper (KiB of RAM above 1 MiB) to size the physical frame allocator. include/multiboot.h has the full struct.

The bridge: _start

/* .bss: reserve a 16 KiB stack */
.section .bss
.align 16
stack_bottom: .skip 16384
stack_top:

.section .text
.global _start
_start:
    mov $stack_top, %esp   ; stack grows DOWN from stack_top
    push %ebx              ; multiboot info pointer
    push %eax              ; multiboot magic
    call kernel_main       ; into C, never expected to return
    cli
1:  hlt
    jmp 1b                 ; if it does return, halt forever

That is the entire assembly-to-C bridge. Note the stack lives in .bss (zero-initialised, takes no space in the file) and esp starts at the top because the stack grows toward lower addresses.

Interview

"Walk me through what happens between pressing the power button and your main running." — CPU starts in 16-bit real mode executing firmware. BIOS runs POST, picks a boot device, loads the bootloader. GRUB reads the filesystem, finds the Multiboot header in the kernel, loads the ELF segments to their link addresses, enables A20, switches to 32-bit protected mode with a temporary GDT, puts 0x2BADB002 in EAX and the info-struct pointer in EBX, and jumps to the kernel entry. The entry stub sets up a stack, pushes those two registers, and calls into C.

03

The linker script

Where the kernel lives in memory, in what order, and why 2 MiB.

The linker's job is to take all the .o files, merge their sections, assign every symbol a final address, and write one ELF. The default script does this for a hosted Linux program. You override it because your constraints are different: fixed load address, no interpreter, a specific section order.

ENTRY(_start)                ; the ELF entry point symbol

SECTIONS {
    . = 2M;                   ; location counter: start placing at 2 MiB
    kernel_start = .;

    .text BLOCK(4K) : ALIGN(4K) {
        *(.multiboot)         ; FIRST — must be in first 8 KiB
        *(.text)
    }
    .rodata BLOCK(4K) : ALIGN(4K) { *(.rodata) }
    .data   BLOCK(4K) : ALIGN(4K) { *(.data) }
    .bss    BLOCK(4K) : ALIGN(4K) { *(COMMON) *(.bss) }

    . = ALIGN(4K);
    kernel_end = .;            ; PMM uses this to avoid the kernel
}

The four sections

SectionHoldsIn the file?
.textExecutable code (and here, the Multiboot header).Yes
.rodataConstants: string literals, const tables like exception_messages[].Yes
.dataGlobals with a non-zero initial value.Yes
.bssGlobals that start at zero — the stack, page_directory, the frame bitmap, the terminal buffer. Just a size; the loader zero-fills it.No (size only)

Why 2 MiB

  • The first 1 MiB is a minefield: the real-mode IVT, the BIOS data area, VGA memory at 0xB8000, option ROMs, the BIOS itself. You never link a kernel there.
  • Historically kernels load at 1 MiB (0x100000), the first "clean" address. This series uses 2 MiB, which also happens to be a 4 MiB-page–friendly boundary and leaves the 1–2 MiB region free.
  • ALIGN(4K) on every section means each starts on a page boundary — needed once paging is on, so you could map .text read-only and .data read-write separately.
In our code

kernel_start / kernel_end are symbols the linker fills in with addresses. C declares them extern uint8_t kernel_end[]; and takes (uint32_t)kernel_end. KFS_3's memory map deliberately puts the heap at 8 MiB and the frame pool at 16 MiB, well clear of a kernel image that ends around 6 MiB (most of that is the 4 MiB terminal scroll-back buffer in .bss).

Interview

"What is .bss and why isn't it in the executable?" — It is zero-initialised static storage. Storing megabytes of zeros in the file would be wasteful, so the ELF only records the section's address and size; the loader (here, GRUB) allocates and zeroes it. That is why a kernel binary can be 40 KB on disk but claim 4 MB of memory.

Just enough x86

The registers, the two assembly syntaxes in this codebase, the calling convention, and how inline assembly talks to C.

Registers you actually touch

Register(s)Role
eax ebx ecx edxGeneral purpose. Conventions: eax holds return values and the first CPUID leaf; ecx is the classic loop counter; edx:eax is the 64-bit result of some ops.
esi ediGeneral purpose; source/destination index for string ops (rep movsb).
espStack pointer — top of the current stack, moves on every push/pop/call/ret.
ebpBase/frame pointer — by convention, a fixed anchor into the current stack frame so locals and arguments have constant offsets.
eipInstruction pointer. Not directly writable; changed by jumps, calls, returns, interrupts.
eflagsStatus + control bits: CF ZF SF OF (arithmetic results), IF (interrupts enabled), DF (string direction), IOPL, and more. Your eflags shell command decodes it.
cs ds es fs gs ssSegment selectors — 16-bit indices into the GDT. cs = code, ss = stack, ds/es = data. In a flat model they all point at "all of memory" but with different privileges.
cr0Control: bit 0 PE (protected mode), bit 16 WP (enforce read-only pages even in ring 0), bit 31 PG (paging on).
cr2On a page fault, the CPU writes the faulting linear address here.
cr3Physical address of the current page directory. Reloading it flushes the TLB.

Two syntaxes, one CPU

This codebase contains both x86 assembly dialects, which trips people up:

AT&T (GAS)Intel (NASM)
Filesboot.sstart.asm
Operand ordermov src, dstmov dst, src
Registers%eaxeax
Immediates$0x100x10
Memory deref(%ebx), 4(%ebx)[ebx], [ebx+4]

GCC's inline __asm__ is always AT&T. The %% you see there ("mov %%cr0, %0") is an escaped % because %0, %1 are operand placeholders.

The calling convention (cdecl / SysV i386)

Every C call in the kernel follows this, and the ISR stubs depend on it:

  • Arguments pushed onto the stack right-to-left, so the first argument is at the lowest address ([esp+4] after the call pushes the return address).
  • The caller cleans up the arguments after the call returns.
  • Return value in eax (64-bit in edx:eax).
  • Callee-saved: ebx, esi, edi, ebp — a function must preserve these. Caller-saved: eax, ecx, edx — assume any call clobbers them.

This is exactly why boot.s can do push ebx; push eax; call kernel_main and C sees (magic, mbi) in that order.

Reading inline assembly

uint32_t cr2;
__asm__ volatile ("mov %%cr2, %0" : "=r"(cr2));
//                   ^template      ^output: "=r" = write-only, any register

__asm__ volatile ("outb %0, %1" : : "a"(val), "Nd"(port));
//                                  ^inputs: val in AL ("a"), port in DX or imm8 ("Nd")

__asm__ volatile ("cpuid"
    : "=a"(a), "=b"(b), "=c"(c), "=d"(d)   // outputs
    : "a"(0));                             // input: leaf 0 in EAX

volatile tells gcc "do not optimise this away or reorder it" — essential for hardware I/O and control-register pokes. The clobber list (third colon) names registers or "memory" the instruction trashes that aren't in the operand lists.

Gotcha

pusha / popa push and pop all eight GP registers in a fixed order (eax, ecx, edx, ebx, original esp, ebp, esi, edi). The struct regs in defs.h is laid out to match pusha followed by the four segment pushes exactly — get the order wrong and every field in your fault handler is garbage.

05

The stack

How call frames are built, what the CPU pushes on an interrupt, and what the stack command is showing you.

Frames

The stack grows downward (toward lower addresses). A call pushes the return address and jumps. A typical function prologue then does:

push %ebp          ; save caller's frame pointer
mov  %esp, %ebp    ; this frame's anchor
sub  $N, %esp      ; reserve N bytes of locals
...
mov  %ebp, %esp    ; discard locals   (or: leave)
pop  %ebp          ; restore caller's anchor
ret                ; pop return address into eip

With ebp fixed for the function's lifetime, argument N is always [ebp + 8 + 4N] and local N is [ebp - ...]. A debugger walks the call stack by following the saved-ebp chain: each [ebp] points at the previous frame's ebp, and [ebp+4] is that frame's return address.

Note

At -O2, gcc often omits the frame pointer (ebp becomes a normal register and code addresses locals relative to esp). That is why the KFS_2 kernel's initial stack shows ebp = 0x00000000 — nothing set it up; _start jumped straight to C.

What an interrupt pushes

When an interrupt or exception fires, the CPU itself pushes a small frame before your handler runs, so iret can resume exactly:

Some exception vectors (8, 10–14, 17) push a hardware error code; the rest don't. The stubs paper over this: vectors without one push $0 first, so struct regs always has an err_code slot at the same offset. After the handler, the common stub restores everything and does add $8, %esp (drop int_no + err_code) then iret, which pops eip/cs/eflags (and esp/ss on a ring change) atomically.

In our code

stack in the KFS_2 shell writes a handful of marker words (0x11111111 … 0xDDDDDDDD) to a local array, then dumps memory upward from esp in the same 4-words-per-row layout as GDB's x/32xw $esp. The esp/ebp cells are coloured; the markers show up green so you can see where "your" data sits among saved registers and return addresses.

Interview

"How does a handler return to exactly where the interrupt happened?" — The CPU pushed eip, cs, and eflags (plus esp/ss if the privilege level changed) when it took the interrupt. iret pops them back in one atomic step. Your stub is responsible for restoring the GP and segment registers it saved, and for removing anything it pushed itself, before executing iret.

06

VGA text mode & printf

The one piece of memory-mapped hardware you can use with zero setup, and how to build a formatter with no libc.

The text buffer

In VGA text mode the screen is memory-mapped at physical 0xB8000: an 80×25 grid of 16-bit cells. Write a value there and the character appears on the next refresh — no driver, no MMIO handshake.

Bits of the cellMeaning
0–7Code point (code page 437).
8–11Foreground colour (16 colours).
12–14Background colour (8 colours).
15Blink (or bright background, depending on mode).
 
static inline uint16_t vga_entry(unsigned char ch, uint8_t colour) {
    return (uint16_t)ch | (uint16_t)colour << 8;
}
static inline uint8_t vga_color(enum vga_color fg, enum vga_color bg) {
    return fg | bg << 4;
}
buffer[row * 80 + col] = vga_entry('A', vga_color(LIGHT_GREEN, BLACK));

The blinking hardware cursor is separate — it is positioned by writing a cell index to CRTC registers via port 0x3D4 (index) / 0x3D5 (data), which is what update_cursor() does.

In our code

The terminal keeps an off-screen screen_t per virtual screen with a large scroll-back buffer, and refresh_display() blits the visible 80×25 window into 0xB8000. KFS_2 adds terminal_set_color() / terminal_reset_color() so gdt, stack, and panics can colour their output.

Building kprintf without a standard library

Variadic functions work in freestanding C because <stdarg.h> is one of the guaranteed headers. The formatter is a loop:

int kvprintf(void (*putc)(char), const char *fmt, va_list ap) {
    for (const char *p = fmt; *p; p++) {
        if (*p != '%') { putc(*p); continue; }
        p++;
        // parse flags (- and 0), then width digits
        switch (*p) {
        case 'd': { int v = va_arg(ap, int);           /* itoa base 10 */ }
        case 'x': { unsigned v = va_arg(ap, unsigned);  /* itoa base 16 */ }
        case 's': { const char *s = va_arg(ap, const char*); ... }
        case 'c': { char c = (char)va_arg(ap, int); ... }  // promoted to int
        }
    }
}

The number conversion is the classic "divide by base, collect remainders, reverse the string." The KFS_2 version adds %p, zero/space padding, and left-justify (%-13s) via one emit_padded() helper. Passing putc as a function pointer lets the same core drive the live screen or a specific virtual screen.

Gotcha

char and short arguments to a variadic function are promoted to int; float to double. So %c must do va_arg(ap, int), not va_arg(ap, char) — the latter is undefined behaviour.

The GDT & segmentation

The table the CPU consults to turn a segment selector into a base, a limit, and a privilege level — and why you still need it even with a flat memory model.

Segmentation, briefly

Before paging, x86's memory scheme was segmentation: an address is segment : offset, and the segment names a region with a base and a size. In real mode this is just base = segment × 16. In protected mode the segment register holds a selector — an index into a descriptor table — and the descriptor carries a 32-bit base, a 20-bit limit, and access rights.

Modern kernels don't use segmentation for memory layout — they set every segment to base 0, limit 4 GiB (the "flat model") and do all real memory management with paging. But you still must define those flat segments, because:

  • The CPU refuses to run in protected mode without a valid GDT and CS/SS loaded from it.
  • The descriptor's DPL (privilege) field is how the CPU knows whether code is ring 0 (kernel) or ring 3 (user).
  • Interrupt gates in the IDT reference a code segment selector — 0x08 in this kernel.

A descriptor, bit by bit

Each GDT entry is 8 bytes with a famously awkward layout (the base and limit are split across non-adjacent fields for 286 backward compatibility):

The KFS_2 GDT has seven entries, and the encodings become readable once you know the byte:

#SelectorAccessMeaning
00x000x00Null descriptor — mandatory, must never be loaded.
10x080x9AKernel code: P=1, DPL=0, S=1, Exec, Read.
20x100x92Kernel data: P=1, DPL=0, S=1, Write.
30x180x96Kernel stack (data, expand-down variant).
40x200xFAUser code: same as #1 but DPL=3.
50x280xF2User data: DPL=3.
60x300xF6User stack: DPL=3.

Granularity byte 0xCF on every entry = G=1 (limit counts 4-KiB units) + D/B=1 (32-bit) + limit's top nibble 0xF. With limit_low = 0xFFFF too, the segment spans 0xFFFFF 4-KiB pages = the full 4 GiB.

A selector is not just an index

The 16-bit value you load into a segment register is: index (13 bits) | TI (1 bit, 0 = GDT) | RPL (2 bits). So GDT entry 1 → selector 1 << 3 = 0x08; entry 2 → 0x10. The bottom two bits are the Requested Privilege Level. Privilege checks use max(CPL, RPL) vs the descriptor's DPL.

TermIs
CPLCurrent Privilege Level — the low 2 bits of CS right now. 0 = kernel, 3 = user.
DPLDescriptor Privilege Level — the privilege stored in a segment/gate descriptor.
RPLRequested Privilege Level — low 2 bits of a selector value, lets the kernel voluntarily act with reduced rights.

Installing it

gp.limit = sizeof(gdt) - 1;      // "limit" = size minus one, always
gp.base  = (uint32_t)&gdt;
gdt_flush();                     // asm: lgdt [gp]; reload segments
gdt_flush:                       ; start.asm
    lgdt [gp]
    mov ax, 0x10                 ; kernel data selector
    mov ds, ax                   ; ...into every data segment reg
    mov es, ax
    mov ss, ax
    jmp 0x08:.flush              ; FAR jump: this is what reloads CS
.flush:
    ret

You cannot mov into CS. The only way to reload it — and thus start fetching instructions through your new code descriptor — is a far jump or far return. That single jmp 0x08:.flush is the moment the CPU starts trusting your GDT.

Gotcha

Entry 0 must be all zeros and no segment register may hold selector 0x00. Loading a data segment with the null selector is legal (it just faults on use); loading CS or SS with it is an immediate #GP. This is a deliberate CPU safety net against uninitialised segment registers.

Interview

"If you use a flat memory model, why have a GDT at all?" — Three reasons: protected mode literally won't run without a valid GDT and a code segment loaded from it; the descriptor's DPL is the mechanism the CPU uses to distinguish ring 0 from ring 3; and IDT gates reference a GDT code selector. You also need it later for a TSS, which is how the CPU finds the ring-0 stack when a user-mode interrupt fires.

"What is the null descriptor for?"

It occupies index 0 so that a zeroed selector value points at a guaranteed-invalid entry. That turns "forgot to initialise a segment register" from a silent bug into a fault. It also gives lgdt a defined entry at offset 0.

08

The IDT, exceptions & ISRs

The table that maps interrupt vector 0–255 to a handler, the 32 CPU exceptions, and the assembly trampolines that make them callable from C.

Interrupt vs exception vs IRQ

  • Exception — the CPU raised it synchronously because an instruction couldn't complete: divide by zero (#DE, 0), invalid opcode (#UD, 6), general protection (#GP, 13), page fault (#PF, 14). Vectors 0–31 are reserved for these.
  • Hardware interrupt (IRQ) — a device asserted a line asynchronously: timer, keyboard, disk. Delivered through the PIC (Part 09).
  • Software interrupt — the int N instruction. Used for syscalls (int 0x80 on classic Linux).

All three funnel through the same IDT: 256 entries, each an 8-byte gate descriptor.

Gate fieldMeaning
offset (16+16)Address of the handler, split low/high.
selectorCode segment to run the handler in — 0x08 (kernel code).
type0xE = 32-bit interrupt gate (clears IF on entry), 0xF = trap gate (leaves IF set). This kernel uses 0x8E = present + DPL 0 + interrupt gate.
DPLMinimum privilege to invoke via int. Kept at 0 so user code can't fake exceptions; a syscall gate would use DPL 3.

Which vectors push an error code

The CPU pushes a hardware error code for exceptions 8, 10, 11, 12, 13, 14, 17 (and 21). For every other vector it pushes nothing. The stubs normalise this:

isr0:                 ; no error code -> push a fake 0
    cli
    push byte 0
    push byte 0        ; vector number
    jmp isr_common_stub

isr8:                 ; CPU already pushed an error code
    cli
    push byte 8        ; just the vector number
    jmp isr_common_stub

The common stub then builds the full struct regs and calls one C function:

isr_common_stub:
    pusha                 ; eax ecx edx ebx esp ebp esi edi
    push ds
    push es
    push fs
    push gs
    mov ax, 0x10          ; ensure kernel data segments
    mov ds, ax
    mov es, ax  &c
    mov eax, esp
    push eax              ; arg: struct regs *
    call fault_handler
    pop eax
    pop gs / fs / es / ds
    popa
    add esp, 8            ; discard int_no + err_code
    iret
In our code

isrs_install() fills IDT entries 0–31 with the 32 stub addresses. fault_handler() in isrs.c looks up exception_messages[r->int_no] and, in KFS_2/3, routes: #BP/#DB → recoverable warning and return; #PF → page_fault_handler() (KFS_3); everything else → fatal panic_from_regs().

Installing the IDT

idtp.limit = sizeof(idt) - 1;
idtp.base  = (uint32_t)&idt;
memset(&idt, 0, sizeof(idt));   // unfilled vectors = not present
idt_load();                    // asm: lidt [idtp]

Same shape as the GDT: a "pointer" register (limit + base) loaded by a dedicated instruction. Vectors you never fill stay zero (not-present); if one fires, you get a #GP or a triple fault, which is a strong hint you forgot a handler.

Interview

"What is the difference between an interrupt gate and a trap gate?" — An interrupt gate clears IF (the interrupt-enable flag) as the CPU takes the interrupt, so the handler runs with hardware interrupts masked; a trap gate leaves IF untouched, allowing nested interrupts. Use interrupt gates for device IRQs (you don't want a re-entrant timer), trap gates for things like debug exceptions where nesting is fine.

"What is a double fault? A triple fault?"

A double fault (#DF, vector 8) is raised when the CPU hits a second exception while trying to deliver a first one — e.g. a page fault whose handler isn't present. If delivering the double fault also fails, the CPU gives up and triple faults, which on real hardware and QEMU means a reset. An unexplained reboot loop in a kernel almost always means a triple fault — usually a bad IDT, bad GDT, or a fault very early in boot.

09

PIC, IRQs, PIT & keyboard

Getting hardware interrupts to your handlers: remapping the 8259, the timer tick, and reading the keyboard.

The 8259 PIC and why you must remap it

Two cascaded 8259A Programmable Interrupt Controllers multiplex 15 device IRQ lines onto the single CPU interrupt pin. The master handles IRQ 0–7, the slave IRQ 8–15, and the slave's output feeds the master's IRQ 2.

Out of reset, the master maps IRQ 0–7 to CPU vectors 0x08–0x0F. That collides head-on with CPU exceptions 8–15 — a timer tick would look like a double fault. So the first thing you do is reprogram the PICs with a four-word init sequence (ICW1–ICW4) to move them to vectors 0x20–0x2F:

outb(0x20, 0x11); outb(0xA0, 0x11);  // ICW1: begin init, expect ICW4
outb(0x21, 0x20); outb(0xA1, 0x28);  // ICW2: master base 0x20, slave 0x28
outb(0x21, 0x04); outb(0xA1, 0x02);  // ICW3: slave is wired to master IRQ2
outb(0x21, 0x01); outb(0xA1, 0x01);  // ICW4: 8086 mode
outb(0x21, 0x00); outb(0xA1, 0x00);  // unmask all lines

Now IRQ 0 arrives as vector 32, IRQ 1 as vector 33, and so on. irq_install() points IDT entries 32–47 at the irq0..irq15 stubs, which share an irq_common_stub nearly identical to the ISR one but calling irq_handler().

End Of Interrupt

The PIC will not deliver another interrupt of equal or lower priority until you acknowledge the current one by writing 0x20 (the EOI command) to its command port. For an IRQ from the slave (≥ 8), you must EOI both PICs:

void irq_handler(struct regs *r) {
    void (*handler)(struct regs*) = irq_routines[r->int_no - 32];
    if (handler) handler(r);
    if (r->int_no >= 40) outb(0xA0, 0x20);  // EOI slave
    outb(0x20, 0x20);                       // EOI master
}
Gotcha

Forget the EOI and that IRQ line goes dead after one interrupt — the keyboard types exactly one character then stops. Send it too early (before reading the device) and you can miss or double-read data.

IRQ 0 — the PIT

The 8253/8254 Programmable Interval Timer has a fixed input clock of 1 193 182 Hz. You program channel 0 with a 16-bit divisor; it then fires IRQ 0 at 1193182 / divisor Hz. KFS_2 sets 100 Hz:

uint32_t divisor = 1193182 / 100;
outb(0x43, 0x36);                 // channel 0, lo/hi byte, mode 3 (square wave)
outb(0x40, divisor & 0xFF);
outb(0x40, divisor >> 8);

The handler just increments timer_ticks; uptime divides by the frequency. This same tick is what a real kernel uses to drive preemptive scheduling.

IRQ 1 — the keyboard

The 8042-style keyboard controller exposes two ports: 0x60 (data) and 0x64 (status/command). On each keypress or release it raises IRQ 1; you read one scan code from 0x60.

  • Scan code set 1: a make code on press, and the same value | 0x80 as the break code on release. So bit 7 tells you press vs release.
  • A leading 0xE0 byte marks an extended key (arrow keys, right-ctrl, …); you read the next byte to identify it.
  • Scan codes are positional, not ASCII. You translate through a lookup table — two tables, actually: kbdus[] and kbdus_shift[] — tracking shift/alt as state across interrupts.
In our code

keyboard_handler() tracks shift_pressed/alt_pressed/extended_scancode as static flags, maps the code to a character, and either feeds the shell (shell_handle_key) or echoes it. ESC is intercepted at the scancode layer to toggle the shell; ALT+arrows switch virtual screens.

Interview

"Why do you remap the PIC?" — Because its power-on vector base (0x08) overlaps the CPU's reserved exception range (0–31). Without remapping, IRQ 0 (timer) is indistinguishable from vector 8 (#DF). You reprogram both PICs to a free base (0x20) via the ICW1–4 sequence so device interrupts land at 32–47.

"Interrupts vs polling — when each?"

Polling (spin reading a status port) is simple and has low latency for one device you're actively waiting on, but wastes 100% CPU and scales terribly. Interrupts let the CPU do other work (or hlt) until a device needs service — essential for a multitasking kernel. The cost is the context-save/restore on every interrupt and the concurrency hazards of re-entrancy. Real drivers often combine both: interrupt to wake up, then poll-drain a queue.

Paging

Turning every address the CPU sees into a lookup through tables you control — the core of KFS_3.

Why paging

  • Isolation. Each process gets its own page tables, so its address 0x40000000 and another process's 0x40000000 map to different physical RAM. One process cannot even name another's memory.
  • Over-commit & demand paging. A page can be marked not-present and its contents kept on disk; touching it faults, the kernel loads it, and execution resumes. This is how you run programs bigger than RAM.
  • Fine-grained rights. Per-page read/write and user/supervisor bits — you can map code read-only and data no-execute.
  • No external fragmentation of virtual space. Physically scattered frames can be mapped to a contiguous virtual range (this is exactly what vmalloc exploits).

The 32-bit two-level walk

With 4-KiB pages, a linear address splits into three fields:

Directory / table entry format

A PDE and a PTE are both 32 bits: the top 20 are a physical frame number, the bottom 12 are flags. The frame number is only 20 bits because everything is 4-KiB aligned — the low 12 bits are always zero, so they're reused for flags.

BitNameMeaning
0PPresent. 0 → any access faults (this is the demand-paging / swap hook).
1R/W0 = read-only. Enforced in ring 0 only if CR0.WP is set.
2U/S0 = supervisor-only (ring 0–2). This is the kernel/user split at page granularity.
3–4PWT, PCDWrite-through / cache-disable for this page.
5AAccessed — CPU sets it on any access.
6DDirty — CPU sets it on write (PTE only). Used to know if a swapped page needs writing back.
7PSPDE only: 1 = this entry maps a single 4-MiB page, no second level.
8GGlobal — TLB entry survives a CR3 reload (needs CR4.PGE).

The TLB

Walking two tables per access would be ruinous, so the CPU caches recent translations in the Translation Lookaside Buffer. The consequence: if you change a page table entry, the CPU may still use the stale cached translation. You must invalidate it:

  • invlpg (addr) — drop the TLB entry for one page (what map_page/unmap_page do).
  • Reloading CR3 — flushes the whole non-global TLB (e.g. on a context switch).

Turning it on

void paging_init(void) {
    // identity-map the first 64 MiB with real 4-KiB pages
    for (d = 0; d < 16; d++) {
        for (e = 0; e < 1024; e++)
            identity_pt[d][e] = ((d*1024 + e) * 0x1000) | PAGE_PRESENT | PAGE_RW;
        page_directory[d] = (uint32_t)identity_pt[d] | PAGE_PRESENT | PAGE_RW;
    }
    load_cr3((uint32_t)page_directory);
    // set CR0.PG (bit 31) + CR0.WP (bit 16)
    write_cr0(read_cr0() | 0x80010000);
}

Identity mapping — what and why

An identity map makes linear address X translate to physical address X. KFS_3 identity-maps the first 64 MiB. Two reasons this is the pragmatic choice for a teaching kernel:

  1. The instant you set CR0.PG, the very next instruction fetch goes through the tables. If the code you're executing isn't mapped, you triple-fault immediately. Identity mapping the kernel means "nothing changes" at the moment of the switch.
  2. To edit a page table you must be able to write to it, which means it must be mapped. If every frame you allocate for a new page table lives in the identity-mapped region, its physical address is a usable pointer.

The "real" design is a higher-half kernel: link the kernel at 0xC0000000+, map it there, and leave the low address space entirely for user processes. KFS_3 skips that to keep the focus on the allocators.

Page faults

On a #PF the CPU writes the faulting linear address to CR2 and pushes an error code whose low bits explain the fault:

Bit01
Ppage not presentprotection violation
W/Rwas a readwas a write
U/Sfault in kernelfault in user

A real kernel's handler inspects this to decide: grow the stack, copy-on-write, load a swapped page, or kill the process. KFS_3's handler decodes it into a readable panic line — page fault at 0xADDR (not-present, write, kernel) eip=….

In our code

map_page(virt, phys, flags) allocates a page-table frame from the PMM if the directory entry is missing, then writes the PTE and invlpgs. virt_to_phys() does the walk in software — the paging shell command uses it to print the PDE, PTE, and resulting physical address for any linear address you give it.

Interview

"Translate 0x40001234 for me." — Split it: dir index = 0x40001234 >> 22 = 256, table index = (0x40001234 >> 12) & 0x3FF = 1, offset = 0x234. CPU reads PDE = mem[CR3 + 256*4], checks Present, takes its frame as the page-table base, reads PTE = mem[pt_base + 1*4], checks Present + permissions, and the physical address is (PTE & 0xFFFFF000) | 0x234. If either Present bit is 0, #PF with CR2 = 0x40001234.

"What is the difference between logical, linear, and physical addresses?"

Logical = segment : offset as written in the instruction. Segmentation turns it into a linear (a.k.a. virtual) address by adding the segment base — in a flat model this is a no-op, so linear = offset. Paging then turns the linear address into a physical one via the page tables. With flat segmentation + paging (every modern OS), only the linear→physical step matters.

Physical memory management

Handing out and reclaiming 4-KiB frames of real RAM — the layer paging and both heaps sit on.

The problem

Paging needs frames for page tables. The heaps need frames for their backing store. Something has to track which physical 4-KiB frames are free. That is the physical memory manager (frame allocator).

How much RAM is there?

You don't guess — the Multiboot info struct tells you. mbi->mem_upper is KiB of contiguous RAM above 1 MiB; the full mmap array gives every region with a type (available / reserved / ACPI). KFS_3 uses mem_upper for simplicity and caps its pool at the 64-MiB identity boundary.

The bitmap allocator

The simplest workable design: one bit per frame, 0 = free, 1 = used. 48 MiB of pool ÷ 4 KiB = 12 288 frames = 1 536 bytes of bitmap, which lives in .bss.

uint32_t pmm_alloc_frame(void) {
    for (i = 0; i < total_frames; i++)
        if (!bm_test(i)) { bm_set(i); return POOL_START + i*0x1000; }
    return 0;                       // out of memory
}
void pmm_free_frame(uint32_t phys) { bm_clear((phys - POOL_START) / 0x1000); }
AllocatorTrade-off
Bitmap (used here)Tiny metadata, dead simple, allocation is O(n) scan. Fine for a hobby kernel.
Free list / stack of framesO(1) alloc/free, but can't easily find contiguous runs and the links cost a pointer per free frame (often stored in the free frame itself).
Buddy allocatorO(log n), naturally handles contiguous power-of-two blocks, some internal fragmentation. What Linux actually uses.

KFS_3's physical map

0x00000000 – 0x00200000   low memory, BIOS, VGA        (identity)
0x00200000 – ~0x00600000  kernel image + page tables  (identity)
0x00800000 – 0x01000000   kernel heap  (kmalloc/kbrk)  (identity)
0x01000000 – 0x04000000   PMM frame pool              (identity)
0x40000000 – 0x50000000   virtual heap (vmalloc/vbrk)  (demand-mapped)

The pool starts at 16 MiB so it can never collide with the kernel or the kernel heap, and ends at 64 MiB so every frame it returns is inside the identity map and therefore directly writable as a page table.

Interview

"You call pmm_alloc_frame() and get 0x2000. What can and can't you do with that pointer?" — 0x2000 is a physical address. You can only dereference it directly if it's covered by the current page tables. In KFS_3 the whole low 64 MiB is identity-mapped, so *(uint32_t*)0x2000 works. In a higher-half kernel you'd have to map it somewhere first (or use a permanent physical-memory window) before touching it.

The kernel heap

kmalloc, kfree, ksize, kbrk — a first-fit free-list allocator over an identity-mapped region.

What a heap allocator is

The PMM hands out whole 4-KiB frames. A heap sits on top and hands out arbitrary-sized chunks from within a larger region, tracking which bytes are in use. The classic Unix model splits this in two layers:

  • brk / sbrk — moves the single boundary ("the break") between the heap and unused address space. Coarse: grow or shrink the whole heap.
  • malloc / free — sub-divide the space below the break into allocations, reusing freed holes.

kbrk

KFS_3's kernel heap occupies a fixed identity-mapped window (8–16 MiB). Because it's identity-mapped, the physical frames are already there — kbrk just moves a pointer and bounds-checks against the 16-MiB limit:

void *kbrk(int32_t delta) {
    uint8_t *old = heap_end;
    if (heap_end + delta > heap_limit || heap_end + delta < heap_start)
        return (void*)-1;
    heap_end += delta;
    return old;                // sbrk semantics: returns the OLD break
}

The free list

Every allocation is preceded by a header. Blocks form a doubly-linked list in address order:

typedef struct block {
    uint32_t magic;           // 0xB10CB10C — detects corruption & bad frees
    uint32_t size;            // payload bytes
    uint32_t free;
    struct block *next, *prev;
} block_t;

kmalloc: walk the list for the first free block with size ≥ request (first-fit). If it's much bigger, split it — carve the tail into a new free block. If nothing fits, kbrk more space and append a block.

kfree: check the magic, mark free, then coalesce — if the next and/or previous block is also free, merge them into one so the space is reusable for a large future request. If the merged block is the last one, hand the memory back with a negative kbrk.

ksize: step back one header from the pointer, verify the magic, return size.

Fragmentation

  • Internal — you asked for 40 bytes, the allocator rounded to 48 (8-byte alignment) plus a 20-byte header. The waste is inside the allocation.
  • External — enough total free space for a request, but no single hole big enough. Coalescing fights this; so do best-fit and segregated size classes.
Beyond first-fit

Production allocators use segregated free lists / bins (glibc, jemalloc), a slab allocator for fixed-size kernel objects (Linux kmem_cache), or a buddy system. All trade metadata and complexity for lower fragmentation and O(1) common paths. First-fit + coalescing is the honest starting point that shows you understand the problem.

Interview

"How does free know how big the block was?" — It doesn't get told. malloc stored the size in a header immediately before the returned pointer; free and ksize subtract the header size from the pointer and read it back. The magic value in that header is also how you catch a double-free or a write that ran off the end of the previous allocation.

The virtual heap

vmalloc and friends — the same allocator, but every page is backed on demand by a physically scattered frame.

The one difference that matters

The kernel heap lives in identity-mapped memory: virtually contiguous and physically contiguous, frames pre-supplied. The virtual heap lives in a region (1 GiB–1.25 GiB) that is not mapped at boot. Growing it means, for each new page:

uint32_t frame = pmm_alloc_frame();          // any free physical frame
map_page(page, frame, PAGE_PRESENT | PAGE_RW);  // stitch it into the address space
memset((void*)page, 0, 0x1000);

Consecutive virtual pages can (and usually do) get non-consecutive physical frames. Shrinking reverses it: unmap_page then pmm_free_frame. Above that, the identical first-fit / split / coalesce allocator runs — the code is literally shared, parameterised by a "grow" function.

In our code

vmalloc 9000 in the shell returns something like 0x40000018 with vsize = 9000 and prints its physical frame — e.g. 0x01000018 — proving the virtual address and the physical frame are unrelated. It spans three pages, each independently mapped.

Interview

"When would you use vmalloc over kmalloc?" — For a large allocation (say a 2 MB buffer) where you only need the CPU to see it as one contiguous range. kmalloc would need 512 physically contiguous free frames, which fragmentation may make impossible; vmalloc stitches 512 arbitrary frames into a contiguous virtual range. You avoid vmalloc for anything a device DMAs into, because the device bypasses the MMU and sees the scattered physical frames.

Kernel panics

There is no process to kill and no shell to return to — so what do you do when something is unrecoverable?

Fatal vs recoverable

The subject is explicit that not every panic is fatal. The distinction:

  • Recoverable — the kernel's invariants are intact and execution can continue. A breakpoint (#BP, int3) or debug exception (#DB) is informational. KFS_2/3 print a yellow warning and iret back.
  • Fatal — an invariant is broken and continuing would corrupt state or loop forever: a page fault in the kernel, a #GP, a failed assertion, out-of-memory where the caller can't cope. Print everything useful, then stop the machine.

What "stop the machine" means

__asm__ volatile ("cli");     // mask interrupts — nothing else runs
for (;;) __asm__ volatile ("hlt");  // halt until an interrupt… which can't come

hlt alone would resume on the next interrupt; cli first makes it permanent. The loop guards against a non-maskable interrupt nudging the CPU past a single hlt.

What to dump

A panic screen is the only debugger you have on real hardware. KFS's panic_from_regs() prints, from the struct regs the ISR captured: the vector and its name, the error code, every GP register, the segment selectors, eflags, and — critically — eip (where it died) and CR2 (for a page fault, what address it touched). With eip and the linker map you can find the exact line.

In our code

panic(fmt, …) takes printf-style args for assertion-style failures; panic_nonfatal(fmt, …) is the recoverable yellow-banner path; panic_from_regs(r) is what the fault handler calls for CPU exceptions. All three set a distinctive screen colour so a panic is unmistakable.

Interview

"Your kernel panics with eip = 0x00102f4a. How do you find the bug?" — Run objdump -d kernel.bin (or check kernel.map) and find which function contains 0x102f4a. Combined with the faulting instruction, the register dump, and CR2 if it's a page fault, that usually pins it to a line. On QEMU you'd also attach GDB (-s -S) and set a breakpoint there for a live look.

Question bank

Rapid-fire, grouped by area. Say the answer out loud before opening the panel.

Toolchain & build

What does -ffreestanding actually change?

It tells the compiler the program runs without a hosted C environment: main loses its special status, the standard library may be absent, and only <stdint.h> <stddef.h> <stdbool.h> <stdarg.h> <float.h> <limits.h> <iso646.h> are guaranteed. It does not stop gcc emitting calls to memcpy/memset/memmove/memcmp, which is why you still implement those four.

Why does the link line end in -lgcc if you're -nostdlib?

libgcc is compiler runtime support, not an OS library: 64-bit divide/modulo helpers (__udivdi3, __moddi3), soft-float, __builtin fallbacks. 32-bit x86 has no div for 64-bit operands, so uint64_t / uint64_t becomes a call into libgcc. It's allowed because it has no OS dependency.

Why can't you use the host's linker script?

It links a hosted executable: entry at _start from crt0, load address in the normal user range, an INTERP segment naming the dynamic loader, and it discards or misplaces custom sections like .multiboot. You need a fixed load address (2 MiB), no interpreter, and .multiboot forced into the first 8 KiB — so you write your own.

Boot

What are the three numbers in the Multiboot header?

Magic 0x1BADB002 (lets the loader locate the header by scanning), flags (request page-aligned modules, a memory map, video info…), and a checksum such that magic + flags + checksum overflows to 0 in 32 bits. The header must be 4-byte aligned within the first 8 KiB of the file.

What state is the machine in when your entry point runs?

32-bit protected mode, paging off, interrupts off, A20 enabled, a temporary GDT loaded, EAX = 0x2BADB002, EBX = physical pointer to the multiboot info struct, ESP undefined. First job: load your own stack pointer.

Real mode vs protected mode in one line each.

Real mode: 16-bit, 1 MiB, seg×16+off addressing, no protection — boot compatibility. Protected mode: 32-bit, 4 GiB, selector→descriptor segmentation with privilege checks, optional paging — where the OS actually lives.

GDT / segmentation

Why is the "limit" field always size − 1?

So that a limit of all-ones describes a segment covering the entire address space rather than a zero-length one, and so the maximum representable size uses every bit. The GDTR, IDTR, and each descriptor all use this "one less than the byte count" convention.

How do you reload CS, and why is it special?

You can't mov into CS. Only a far jump, far call, far return, or iret changes it — because changing CS means changing the privilege level and code descriptor atomically with the instruction pointer. After lgdt you do jmp 0x08:label to start executing through the new code segment.

CPL, DPL, RPL?

CPL = your current ring (low 2 bits of CS). DPL = the ring stored in a descriptor. RPL = low 2 bits of a selector value, a way to weaken a request on purpose. A data access is allowed when max(CPL, RPL) ≤ DPL.

Interrupts

Exception vs interrupt vs trap?

Fault: reported before the faulting instruction, which can be restarted (page fault). Trap: reported after (breakpoint, int3). Abort: severe, no reliable restart (double fault, machine check). "Interrupt" loosely means any of these plus asynchronous device IRQs; all go through the IDT.

Which exception vectors push an error code?

8 (#DF), 10 (#TS), 11 (#NP), 12 (#SS), 13 (#GP), 14 (#PF), 17 (#AC), 21 (#CP). Your stubs push a dummy 0 for all the others so the stack frame is uniform.

What does iret pop?

eip, cs, eflags — and additionally esp, ss if the interrupt caused a privilege-level change (user→kernel). Your stub must have already restored GP + segment registers and removed its own pushes.

PIC / IRQ

Master/slave wiring?

Two 8259s. Master owns IRQ 0–7 and drives the CPU pin; slave owns IRQ 8–15 and feeds the master's IRQ 2. So any IRQ ≥ 8 needs an EOI to both chips.

Where does the PIT frequency 1193182 come from?

It's the legacy 14.31818 MHz NTSC colorburst crystal divided by 12 — a historical accident now frozen into every PC. You divide it further with a 16-bit reload value to pick your tick rate.

Paging / memory

What's in CR3 — a virtual or physical address?

Physical. The MMU can't use a virtual one — resolving it would require the very tables it's trying to find. Same for the frame numbers inside every PDE/PTE: all physical.

You changed a PTE and the old mapping still works. Why?

The TLB cached the old translation. Issue invlpg for that page, or reload CR3 to flush everything non-global.

What are the ways to handle a page fault?

Map a new zero page (lazy allocation / stack growth), copy a shared page and make it writable (copy-on-write), read a page back from swap/disk, satisfy a memory-mapped file, or — if the access is genuinely illegal — deliver SIGSEGV / kill the process. In a kernel with no processes, it's a panic.

kmalloc vs vmalloc, physically?

kmalloc: contiguous in both virtual and physical space. vmalloc: contiguous virtually, arbitrary physically — it maps scattered frames into a contiguous virtual window. DMA-capable buffers must be kmalloc (or from a DMA pool) because devices see physical addresses.

Internal vs external fragmentation?

Internal: rounding/headers waste space inside an allocation. External: total free ≥ request but no single contiguous hole is big enough. Coalescing and size-class allocators target external; tighter rounding targets internal.
